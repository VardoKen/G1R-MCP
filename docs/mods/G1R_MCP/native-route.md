# Нативный маршрут — 1.0.0-dev.103

Актуализировано **05.11.2026** по рабочим исходникам и отдельным локальным и игровым подтверждениям. Рабочая версия — **1.0.0-dev.103**, каталог содержит **51 MCP-инструмент**, целевая публичная версия — **1.0.0**. Инструмент предназначен для исследования API и состояния игры, разработки и отладки официальных модов `GothicMod.json`/AngelScript. Готовность к переносу модов с UE4SS — промежуточный рубеж этого назначения; сам перенос конкретных модов и публичная поставка являются отдельными задачами.

## Текущая цепочка

```text
MCP-клиенты / чаты Codex
  ↕ Streamable HTTP 127.0.0.1:27124/mcp
Один общий G1R MCP Server
  ↕ TCP 127.0.0.1:27123, uint32BE + UTF-8 JSON
G1R_MCP.dll в проверенном процессе игры
  ↕ очередь на подтверждённом FEngineLoop::Tick
UObject / UFunction / ProcessEvent
  ↕ нативные и отражённые AngelScript-функции
```

DLL и loader работают независимо от UE4SS. `g1r_mcp_loader.exe` загружает DLL из выбранного runtime-каталога в точно проверенный игровой процесс. DLL остаётся загруженной до завершения этого процесса; повторная загрузка того же модуля не создаёт второй мост. Перезагрузка DLL в работающей игре не является поддержанным способом обновления.

Официальный `G1RMCPDevelopmentHelpers` — отдельный пакет `GothicMod.json`/AngelScript. Основная DLL загружается development-loader; текущий runtime-комплект не доказывает её доставку и автоматическую загрузку через Steam Workshop. Наличие Workshop ID в локальном пользовательском manifest также не является подтверждением публикации.

## Общий сервер и установленный wheel

Текущая конфигурация Codex использует URL `http://127.0.0.1:27124/mcp`. Из рабочей базы сервер запускают существующим `tools/start_shared_mcp.ps1 -Json`; повторный запуск проверяет идентичность действующего процесса и переиспользует его. Windows-окружение может иметь два связанных процесса Python — launcher виртуального окружения и HTTP worker. Они общие для всех чатов. Закрытие чата не останавливает сервер; прямой stdio-запуск создаёт отдельный дочерний сервер и не заменяет общий HTTP-маршрут.

Поставка состоит из Python wheel и отдельной runtime-папки с DLL, loader и PowerShell-инструментами. Canonical runtime dev.103 установлен; runtime-комплект и wheel dev.103 подготовлены. Проверенный комплект dev.102 сохранён. Ранее проверенный `g1r_mcp-1.0.0.dev99-py3-none-any.whl` остаётся историческим consumer-результатом. Wheel устанавливается в отдельное окружение; DLL и инструменты берутся из `--runtime-root`. `--modkit-root` задаёт совместимые официальные исходники, `--workspace-root` — редактируемые пакеты.

Для установленного Python-пакета команда общего сервера имеет вид:

```powershell
g1r-mcp --transport streamable-http --host 127.0.0.1 --port 27124 `
  --modkit-root '<официальный Modkit>' `
  --workspace-root '<рабочие пакеты>' `
  --runtime-root '<runtime-комплект>' `
  --game-root '<установленная игра>'
```

Все пути указываются для конкретного окружения. `g1r_status.server.runtime_root` показывает фактически выбранный каталог. Сам сервер игру не запускает. Runtime-папку сохраняют целой; создание окружения и записей внутри неизменяемого комплекта нарушает его manifest. Для работы с пакетами и игровым staging используют отдельную рабочую базу. Скрипты запуска/остановки shared MCP рассчитаны на рабочую копию с локальной `.venv` и соседним Modkit; установленный wheel с внешним runtime запускают приведённой CLI-командой.

## Рабочий контракт

Начало работы: `g1r_status` → `g1r_capabilities`. Эти инструменты возвращают серверный контракт, но не проверяют живую игру. `g1r_native_status` проверяет DLL, hook, Tick и состояние нативного канала. Для нового development-сеанса используются рецепт и SHA manifest, процессная идентичность, загрузка DLL с ожидаемым SHA, затем проверка готовности. HTTP-управление одной игрой требует существующей заявки владельца; изменения общего пакета и редкие обновления сервера согласуют между чатами.

51 инструмент охватывает исходники и API Modkit, создание и редактирование официальных пакетов, ScriptPatches, экспорт с ZIP/manifest, диагностику компиляции, development-сеанс, типизированные игровые вызовы, чтение состояния, снимки и наблюдения. Полные аргументы, результат, побочные эффекты и требования доступны через `g1r_capabilities.tool_contracts`; точные типы конкретной функции подтверждаются `g1r_object_functions` и `signature_token`. Токен проверяет контракт вызова в общей native-сессии и не является разрешением отдельному чату.

`g1r_read_struct` и `g1r_read_array` читают собственные отражённые поля, включая поддержанные вложенные структуры и массивы; дочерние ошибки и частичный результат сохраняются. Их consistency соответственно `copied_bytes_then_metadata_revalidated` и `single_tick_sequential`. Страницы и последовательные чтения не объявляются атомарным снимком. Чтение вложенного типа не доказывает возможность передать этот тип в `ProcessEvent`: входные, выходные и возвращаемые параметры имеют отдельные проверяемые контракты. [Подробные операции и типы](local-tools.md).

Ссылки проверяются по identity и serial. Поколение мира отслеживает отражённую ссылку `GameEngine.GameViewport.World`; наблюдение ссылки не означает ReadyForPlay. Поколение AngelScript повышается после наблюдаемого успешного возврата native reload, что не доказывает компиляцию конкретного исходника. Смена мира инвалидирует world-bound ссылки; успешный reload — script-bound объекты и script CDO. Нативные CDO и asset-ссылки сохраняются по соответствующему контракту. Наблюдения имеют терминальные причины `world_changed`/`script_reloaded`; HTTP disconnect и native reconnect имеют разные последствия, описанные в каталоге.

Изменения staging через `g1r_apply_staged_file` не подтверждают компиляцию сами по себе. Игра компилирует AngelScript при запуске; исторически подтверждённый hot reload относится к телам функций. ScriptPatches можно подготовить, структурно проверить и экспортировать локально. Историческая изолированная серия dev.28 (`artifacts/dev28-combined-result.json`) подтвердила результаты `20` для patch activation и `11` для base patch; это подтверждение двух конкретных проб, а не любых пакетов. Применение выбранного пакета оценивается по игровой диагностике и результату. Отдельный универсальный compiler API не заявляется.

### Реализованная цепочка

```text
ИИ / MCP-клиент
  ↕ Streamable HTTP 127.0.0.1:27124/mcp
Один общий G1R MCP Server для всех чатов
  ↕ TCP 127.0.0.1:27123, uint32BE + UTF-8 JSON
G1R_MCP.dll в процессе игры
  ↕ ограниченная очередь из FEngineLoop::Tick
UObject / UFunction / ProcessEvent
  ↕
Нативные и отражённые AngelScript-функции игры
```

DLL не зависит от UE4SS и не копируется в игру. `g1r_mcp_loader.exe` загружает её из `build/native/Release/` в проверенный игровой PID. Загрузчик проверяет путь/архитектуру процесса, собственный путь DLL и фактический системный модуль `LoadLibraryW`; повторная загрузка того же файла не увеличивает число подключений.

DLL живёт до завершения процесса. `FreeLibrary` и остановка/удаление перехвата в работающей игре не поддерживаются. Чтобы отключить мост, закрыть игру и запустить её без загрузчика. Для пересборки DLL закрыть игру: Windows удерживает загруженный файл.

### Подключение

Из корня подпроекта:

```powershell
uv sync --locked
.\tools\build_native.ps1
.\tools\start_g1r_development.ps1
```

После открытия главного меню:

```powershell
.\tools\load_native.ps1
.venv\Scripts\python.exe -B tools\probe_native_route.py --enable --call-verified-as
```

`start_g1r_development.ps1` использует Steam AppID `1297900`, сохраняет `-FromModManagementUI` и разовые параметры разработки. Существующий выбор модов, Steam LaunchOptions и cache не изменяются. `load_native.ps1` только подключает DLL к уже запущенной игре. Выполнение `--enable` до готовности игры может не сразу дать `ready`; probe ограниченно ждёт подтверждённый Tick, не повторяя игровые действия.

Для всех чатов Codex используется один общий сервер. Из корня подпроекта:

```powershell
uv sync --locked
.\tools\start_shared_mcp.ps1 -Json
```

Глобальная конфигурация Codex на этом ПК содержит:

```toml
[mcp_servers.g1r_mcp]
url = "http://127.0.0.1:27124/mcp"
startup_timeout_sec = 30
tool_timeout_sec = 60
```

CLI текущего приложения подтвердил включённое URL-подключение. Повторный запуск переиспользует процесс, проверив PID, время создания, EXE, командную строку и владельца порта. В Windows постоянно работают Python-сервер и загрузчик `.venv`; новые чаты не добавляют процессов моста. Все HTTP-сессии используют одну рабочую базу и один native TCP-клиент. Закрытие одного чата не закрывает общий сервер.

Сервер не запускает игру. После перезагрузки Windows выполнить команду запуска; остановка — `.\tools\stop_shared_mcp.ps1 -Json`. Автозапуск Windows не установлен. HTTP слушает только `127.0.0.1`, проверяет Host/Origin; отдельный bearer-токен не настроен. Native-операции сериализуются, рабочие изменения используют существующие блокировки и SHA-предусловия. Изменения одного пакета и управление одной игрой нужно согласовывать между чатами: отдельного игрового мира для каждого чата нет.

Уже открытые Codex-сессии могут сохранять прежнее stdio: открыть новую сессию или перезапустить Codex. Проверка `g1r_status` должна вернуть `transport=streamable-http`, версию `1.0.0-dev.14`. Старые stdio-экземпляры остановлены; остальные MCP-подключения сохранены.

Для отдельного stdio-клиента остаётся прежний режим:

```json
{
  "command": "C:/Users/Vardo/Documents/G1R Mods/G1R MCP/.venv/Scripts/python.exe",
  "args": [
    "-B", "-m", "g1r_mcp.server",
    "--modkit-root", "C:/Users/Vardo/Documents/G1R Mods/G1R-Modkit",
    "--workspace-root", "C:/Users/Vardo/Documents/G1R Mods/G1R MCP",

```

В сессии сначала `g1r_native_status`; если DLL загружена, но hook ещё не установлен — один `g1r_native_enable`, затем проверка `ready`. Эти инструменты не запускают игру и не выполняют загрузчик.

### Нативные инструменты

| Инструмент | Назначение |
| --- | --- |
| `g1r_native_status` | Живая версия, проверенный EXE, состояние hook, Tick и игрового потока |
| `g1r_native_enable` | Установить перехват и очередь Tick в уже загруженной DLL; повтор при включённом hook не устанавливает второй |
| `g1r_find_objects` | Поиск по части имени/класса, ограниченный список и непрозрачные ссылки |
| `g1r_object_properties` | Отражённые свойства либо точная выборка `property_names`; порядок и недоступные записи сохраняются |
| `g1r_read_array` | Ограниченная копия страницы отражённого массива с продолжением и отдельными ошибками элементов |
| `g1r_read_struct` | Копия трёх числовых компонентов XYZ либо Pitch/Yaw/Roll по фактическим метаданным |
| `g1r_object_functions` | Функции, параметры и `signature_token` полного поддержанного контракта |
| `g1r_invoke` | Один явный `ProcessEvent` на проверенном объекте с поддержанной сигнатурой |
| `g1r_snapshot` | Выбранные свойства до 16 объектов, скопированные последовательными чтениями на одном Tick |
| `g1r_compare_snapshots` | Локальное сравнение копий: изменения значений, типов, охвата и неизвестные результаты |
| `g1r_watch_start/read/stop/forget` | Наблюдение свойств на Tick с явным сроком, интервалом, буфером и подтверждённой остановкой |

Поддержаны входные `bool`, `int32`, `float`, `double`, UObject/Class-ссылки, `null`, числовые enum/Byte и FName из существующего `NameProperty` через `name_from`. Возврат: скалярные целые/вещественные, `bool`, `FString`, FName, числовые enum/Byte и UObject/Class-ссылки. Строковый результат копируется и освобождается игровым allocator. Входные FString, структуры, массивы и out/ref пока отвергаются; строка или `null` не являются FName-входом. Произвольная компиляция или выполнение глобальных AngelScript-функций не реализованы: доступ осуществляется через отражённые UFUNCTION.

Имя аргумента берётся из `g1r_object_functions`, а не угадывается по исходникам. `g1r_invoke` отмечен как потенциально изменяющий и неидемпотентный. Фактические эффекты определяются конкретной функцией; присутствие функции не доказывает безопасный вызов.

### Снимки, наблюдения и собственный AngelScript-пакет

Проверено 30.10.2026: реальный MCP stdio-клиент получил 23 инструмента, скопировал выбранные bool-свойства CDO `CM_Attack`, сравнил снимки и прошёл `start → read → stop → read → forget`. ### Сессия и ограничения

- Один активный TCP-клиент, один запрос в полёте. MCP-сервер держит постоянное соединение; отдельная диагностическая утилита должна завершить соединение перед работой сервера.
- Ссылки и наблюдения принадлежат текущей сессии. После reconnect искать объекты заново. При лимите реестра сервер возвращает `handle_limit`, сохраняя существующие ссылки. Disconnect прекращает дальнейшие выборки и очищает владельца на игровом потоке.
- Проверяются слот, указатель, internal index, класс, имя и признаки начала/завершения уничтожения. С dev.9 строго сравниваются наблюдаемые serial объекта и класса вместе с identity класса, включая zero. Serial не назначается; zero не защищает от ABA, отдельное поколение мира не подтверждено.
- Кадр до 1 МиБ, глубина JSON ограничена; 1024 уникальных request ID на соединение. Повтор ID не вызывает обработчик второй раз, после предела соединение закрывается.
- Очередь ограничена восемью заданиями, один запрос на Tick. Ожидание — 2,5 секунды. Ещё не начатая работа отменяется; уже начатая после timeout может закончиться. Клиент не повторяет команду и сообщает `may_have_executed`.
- Действия исполняются только в первом подтверждённом потоке Tick. Нет маршрута исполнения игровых вызовов из сетевого потока.
- Частичный/неподдержанный результат отражён в ответе. Не все свойства и функции охвачены. Полный поиск объекта при отсутствии раннего совпадения может заметно занять кадр.
- Узкие не-ASCII FName и сложные свойства пока не имеют полного проверенного покрытия.
- Сбои игры возможны. В ходе разработки были ранние завершения процесса; после явного включения hook и готовности главного меню текущая вертикаль повторно прошла. Длительная работа, смена мира, загрузка сохранения и широкие игровые действия пока не проверены.

Диагностические `native-phase.log` и `native-tick.log` записываются рядом с DLL в игнорируемом `build/`. VEH только фиксирует адрес исключения и передаёт его дальше, не проглатывая сбой игры.

Аргумент и источник имеют точную форму без лишних ключей. Источник — `NameProperty` размером 8 байт с `ArrayDim=1` в пределах подтверждённого владельца; копируются существующие 8 байт без создания имени или поиска строки по FNamePool. Непосредственно перед `ProcessEvent` повторно проверяются источник, layout, serial identity и значение. При изменении источник отвергается до вызова. Строки, `null`, FString-входы и произвольное создание FName не поддержаны.

### Контракт вызова — dev.14

Для проверенного вызова прочитайте `g1r_object_functions`, выберите запись с `signature_status=complete` и передайте её `signature_token` в `g1r_invoke.expected_signature_token`. DLL повторно сверяет полный отражённый контракт и владельцев перед `ProcessEvent`; неверный/чужой/устаревший токен отвергается до исполнения. Токен не даёт доступ к новым типам и не является разрешением HTTP-чату. Без этого аргумента сохраняется прежний путь вызова.

Все HTTP-чаты используют общую native TCP-сессию. Reconnect отзывает handles и токены для всех клиентов; владение управлением игрой по-прежнему относится только к start/stop/restart/load. Для компактного чтения используйте `g1r_object_properties.property_names`. [Формат, ограничения токенов и выборки](local-tools.md#проверенная-сигнатура-и-выборка-свойств--dev14).
