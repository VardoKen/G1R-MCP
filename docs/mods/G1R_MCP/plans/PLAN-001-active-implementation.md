## 1. Цель и исходные границы

Создать рабочий инструмент разработки модов Gothic 1 Remake через MCP. AngelScript остаётся игровой средой, связь сейчас обеспечивает собственная нативная DLL. Вся рабочая база — внутри самостоятельного Git-подпроекта `G1R MCP/`.

Пользователь выбрал Modkit / AngelScript, затем прямо поручил собственный нативный маршрут с приоритетом быстрого рабочего результата, даже при экспериментальной стабильности. Сейчас инструмент предназначен для себя, подготовка публичного выпуска не требуется. Целевой номер 1.0.0 сохраняется для последовательности dev.N. В dev.2 связь, игровой поток, объекты и существующий AngelScript-вызов подтверждены; полный инструмент ещё развивается.

**Первая рабочая вертикаль подтверждена:** внешний MCP-сервер → TCP → DLL → FEngineLoop::Tick → объект/функция текущей игры → структурированный ответ. Собственный официальный AngelScript-пакет для этого не потребовался; вызвана существующая отражённая функция. Это промежуточная точка, не завершение всего плана.

**Согласованный полный объём:** каталог API и возможностей, инструменты состояния и объектов, наблюдения, типизированные действия и средства разработки модов: работа с исходниками/пакетами, диагностика, компиляция, перезагрузка и проверка результата. Конкретные команды выводятся из подтверждённого API. Возможности создания/cooking ресурсов в отдельном редакторе рассматриваются как связанный контур по результатам исследования; игра не подменяет редактор. Невозможная функция обозначается ограничением и требует решения о результате, а не молчаливого сокращения полного объёма.

План не предполагает самостоятельное изменение механик, баланса или пользовательского контента. Сохранения, постоянная игровая конфигурация, глобальные настройки UE4SS и публикация остаются отдельными объектами разрешений. Средства работы с разрабатываемыми модами входят в цель инструмента, но изменение конкретного пользовательского мода требует соответствующего поручения. Произвольный `eval`, универсальная runtime-рефлексия и доступ ко всем скриптовым контекстам не считаются доступными возможностями без доказательств.

### Подтверждённое продолжение 30.10.2026

Пользователь поручил минимально пригодный мост для начала переноса всех UE4SS-модов на официальный формат 31.10.2026, использовать параллельных агентов и продолжать разработку до его прямой команды остановиться. Все необходимые действия для разработки и проверки разрешены, включая тестовые пакеты и перезапуски. Сам перенос модов этим поручением ещё не начат; публикация остаётся отдельной стадией.

В dev.3 реализованы создание/редактирование пакетов, копируемые снимки и сравнение, ограниченные наблюдения с очисткой владельца. Через реальный MCP проверены чтение, stop/forget и 23 инструмента. Новый официальный пакет с `ReadProbeValue()` вернул `1`, после изменения тела — `2` без restart. Неподтверждённый debugger/compiler API не подменяется этим успешным экспериментом.

## 3. Как план будет оставаться активным

Это способ ведения конкретного PLAN-001 в рамках существующих правил проекта, а не новый регламент проекта.

После существенного результата исследования или законченного изменения обновляются затронутые этапы: фактический результат, источник, открытый вопрос, выбранная ветка и следующий шаг. Неподтвердившаяся гипотеза отмечается отрицательным результатом; её зависимые шаги пересматриваются. Неудачная проверка не исчезает из истории и не превращается в скрытый fallback.

Для текущего этапа используются статусы: `не начат`, `в работе`, `ожидает решения/среды`, `подтверждён`, `пересмотрен`, `отменён`. Статус `подтверждён` требует выполнения критериев этапа и ссылки на доказательство. Наличие API, успешная автономная проверка и успешный вызов в игре отмечаются раздельно.

Каждый результат записывается по краткой форме:

| Поле результата | Содержание |
| --- | --- |
| Дата и этап | Когда и что проверено |
| Среда / исходники | Сборка игры, ревизия Modkit, рабочая версия моста или конкретный commit |
| Проверяемая гипотеза | Одно проверяемое утверждение |
| Метод и источник | Команда, автономный сценарий, официальный API или разрешённая игровая проба |
| Наблюдение | Факт, включая отказ и границы результата |
| Вывод | Подтверждено / опровергнуто / остаётся неизвестным |
| Влияние на план | Изменившийся критерий, зависимость, вариант или следующий шаг |

Большие логи и дампы остаются в игнорируемом `artifacts/`, если появятся; постоянная документация хранит краткий вывод и воспроизводимый способ проверки. Отдельные документы источников, контрактов и тестов создаются тогда, когда появляется соответствующий результат. План ссылается на них и не копирует их целиком.

При существенном изменении плана увеличивается редакция (`R1`, `R2`, далее); поле текущей редакции, активный индекс и единый реестр синхронизируются в одном коммите. Обычное обновление статуса не требует нового плана или номера. Документация фиксируется с относящимися к задаче изменениями.

Активность позволяет самостоятельно уточнять порядок, конкретные сигнатуры и методы проверки внутри согласованного объёма. Изменение основы AngelScript, рабочей среды, назначения первой версии, архитектуры или существенное расширение функций выносится на решение пользователя. Прямо согласованные решения сохраняются при следующих редакциях. После завершения, отмены или иной обработки PLAN-001 переносится в архив, а все индексы обновляются одновременно.

## 5. Э0 — целевая среда, объём и версии

**Результат:** проверяемая спецификация среды и понятный объём первой реализации.

Предстоящие действия:

1. Определить точную сборку установленного обновления игры по доступным метаданным; отдельно зафиксировать ревизию Modkit и свидетельства их соответствия. Чтение установленных файлов не означает разрешения на изменение.
2. Сопоставить два назначения: инструмент исследования в development mode и мост для обычного запуска. До Э1 это кандидаты; рабочая среда выбирается по доказательствам и решению пользователя, если последствия различаются существенно.
3. Уточнить потребности первой версии: необходим ли один клиент или несколько независимых клиентов, какие сведения о состоянии игры приоритетны, входят ли наблюдения и действия в первый публичный комплект.
4. Выбрать одну полезную операцию чтения для первой вертикали по подтверждённым классам и сигнатурам. Не использовать выдуманный игровой контракт или действие с сохранениями как проверку связи.
5. Согласовать целевую публичную версию **до первого рабочего кода игрового мода/сервера**. При создании исполняемого прототипа, который становится рабочей базой, уже начинается `dev.1`; название «прототип» не отменяет правило версий.
6. Проверить, принимает ли официальный дескриптор используемый формат версии, включая `-dev.N`. При несовместимости разрешить противоречие до создания рабочего пакета, не скрывать расхождение версии кода и дескриптора.
7. Сверить локальное окружение и выбрать язык, MCP SDK, зависимости и запуск внешнего сервера. Python и существующие наработки — кандидаты, а не заранее принятый стек. Не копировать UE4SS-исполнитель и его зависимости в новый backend.

**Подтверждение:** версии и источники сведений, таблица возможностей с точными сигнатурами, согласованные решения об объёме и версии. Неизвестные параметры обозначены явно.

**Условие перехода:** исследование Э1 имеет определённую целевую среду и границы. До рабочего кода согласована версия; до живой проверки получены необходимые прямые поручения. Если без исследования нельзя выбрать обычный или development запуск, в Э1 проверяются оба кандидата, а полноценная реализация ждёт выбора.

**Фактический результат R2–R3:** public target 1.0.0 и полный объём согласованы. Steam build 26295476 и совпадение всех 7 280 Script-файлов с Modkit установлены воспроизводимым инструментом. Для внешнего локального сервера выбран Python 3.11+ и официальный MCP SDK 2.3.0, зависимости закреплены `uv.lock`; проверено Python 3.14.6. Первое рабочее изменение получает 1.0.0-dev.1. В официальном дескрипторе поле `modVersion`, а совместимость — `dependencies/requiredVersion`; принятие `1.0.0-dev.N` загрузчиком не проверено. Кандидаты первой операции подтверждены примерами: игровое время и координаты игрока, но не вызваны в игре.

## 6. Э1 — доказать канал связи и жизненный цикл

**Результат:** минимальная воспроизводимая связь с обработчиком официального мода и описание её ограничений.

**Текущий выбранный маршрут R5:** по прямому поручению пользователя автономная DLL без UE4SS, TCP и очередь FEngineLoop::Tick. Через MCP уже вызвана существующая AngelScript UFUNCTION. Следующая матрица сохраняет исследовательские варианты первоначального плана; отсутствие официального канала больше не блокирует внутренний инструмент.

### 6.1. Сравнение вариантов

| Кандидат | Что надо доказать | Решение по отрицательному результату |
| --- | --- | --- |
| Официальный сетевой/IPC API, доступный игровому AngelScript | Реальная доступность, обе стороны обмена, формат сообщений, режим запуска, контекст обработки и завершение | Зафиксировать отсутствие/отказ; не подменять его недокументированной DLL |
| Debugger / development channel | Протокол, доставка именно в обработчик нашего мода и ответ без постоянной остановки игры на breakpoint | Если пригоден лишь для отладки или требует иной среды, описать ограничение и получить решение |
| Иной обнаруженный официальный механизм | Надёжный источник и такое же минимальное доказательство, как для остальных кандидатов | Не считать официальную принадлежность достаточным доказательством пригодности |
| Файловый mailbox | Не выбран для проверки как автоматический запасной вариант | Возвращение ранее отвергнутого механизма требует прямого решения пользователя |

Для прямого VM-eval и произвольной компиляции подтверждения по-прежнему нет. Нативная загрузка DLL и loopback TCP прямо выбраны пользователем; она исполняет игровые запросы в Tick, а не на сетевом потоке. UE4SS и файловый fallback не добавляются.

### 6.2. Последовательность проверки

1. Проверить bindings и официальные материалы; для каждого кандидата записать точный доступный API, источник, режим запуска и ограничения.
2. Для отладочного канала изучить документированный протокол и реализацию официального инструмента, если они доступны; отличать управление debugger от команд нашего мода.
3. Найти самостоятельную точку жизни мода: загрузка, готовность мира, обработка, завершение. Не выбирать `Tick`, таймер или Inheritance Injection только по наличию примера. Замена базовых игровых классов требует обоснования и решения об архитектуре.
4. Подтвердить допустимый контекст игровых вызовов. Если транспорт обрабатывается вне него, определить доказанный способ передачи работы; не считать наличие очереди доказательством game-thread исполнения.
5. Перед кодом пробы описать минимальный формат запроса/ответа, ошибки и выбранные ограничения. После разрешения на рабочий код создать минимальный обработчик и внешний проверочный клиент. Цепочка: идентифицированный запрос → обработчик → одна операция чтения → структурированный ответ с тем же идентификатором. Полный контракт Э2 развивается на основании результатов, а не возникает неявно внутри прототипа.
6. Проверить загрузку мода и связь отдельно от готовности игрового мира. Обработчик должен объяснять отсутствие готовой среды, а не выдавать открытый канал за готовность игровых команд.
7. В разрешённой игровой среде проверить отключение, подключение, смену мира и перезагрузку тела функции. Изменения классов/defaults/`UPROPERTY` учитываются как требующие restart; не запускать его без прямого поручения.

### 6.3. Доказательства и измерения

Минимальный успешный обмен дополняется проверками неизвестной операции, повреждённого/слишком большого сообщения, timeout, позднего ответа и отключения. Для каждого кандидата фиксируются корреляция, наблюдаемая задержка, верхний проверенный размер сообщения, нагрузка на обработку кадра и поведение очереди. Лимиты и бюджет обработки выбираются по измерениям и назначению, без произвольных «требований» к миллисекундам.

Число клиентов и параллельных запросов должно соответствовать выбранному объёму. Если канал допускает только одно соединение, отдельно оценить возможность обслуживания нескольких MCP-клиентов через внешний сервер; не смешивать идентичность серверного соединения с владельцами их работ.

**Условие завершения:** обмен воспроизводим на зафиксированной сборке; подтверждён обработчик и контекст исполнения; известны поведение до готовности мира и ограничения завершения. Кандидаты сравнены. Выбран канал, а существенная развилка режима/архитектуры разрешена пользователем.

**Фактический результат R2:** созданы диагностический кодек, разовая проба и командный Steam-запуск. В текущем маршруте Steam → bootstrap → игра с `-FromModManagementUI -as-development-mode -as-ignore-precompiled-data -as-exit-on-error` слушающих TCP-портов нет, 27099 возвращает connection refused. Первые прямые запуски были неверным контекстом и не служат доказательством невозможности канала. Alkimia [подтвердила отсутствие LSP в версии 1.1 и его добавление в следующем обновлении](https://github.com/AlkimiaInteractive/G1R-Modkit/issues/1#issuecomment-6520702135). `FConsoleCommand` статически проверен: обнаруженный ctor не регистрирует обработчик. Прямой сетевой AngelScript API и встроенный Unreal Remote Control backend не подтверждены. Минимальный обмен не выполнен. Независимые локальные инструменты могут развиваться, а сетевой официальный кандидат ожидает обновления; иная архитектура требует решения. Подробности и ограничения: [результаты Э0–Э1](../references/2026-10-30-environment-and-transport.md).

## 7. Э2 — контракт протокола и операций

**Результат:** документированный контракт между сервером и игровым модом, адаптированный к доказанному каналу.

Формат кадров, сериализация и численные пределы выбираются после Э1. Семантика из MCP to UE4SS полезна, но его framing, лимиты и версия протокола не копируются автоматически.

Описать:

- согласование версии, идентичности моста, сборки и доступных возможностей;
- тип сообщения, уникальный идентификатор запроса, имя операции, схему параметров и результата;
- отдельные идентификаторы соединения, клиента-владельца, длительного выполнения, подписки и ссылки на объект там, где они нужны;
- идентичность процесса/среды и поколения. Смена мира, скриптового контекста и restart рассматриваются отдельно; модель поколений выводится из проверенного lifecycle;
- стабильные коды ошибок и структурированные причины, чтобы клиенту не требовалось разбирать текст;
- границу принятия запроса, начало работы, успешный/ошибочный итог и неопределённость после потери связи;
- эффекты операции: не применены, применены, неизвестны. Ошибка упаковки ответа после вызова не означает, что действие не происходило;
- различие прекращения пользовательской работы, отмены, удаления/нейтрализации регистрации и завершения уже вошедшего обработчика;
- лимиты размера, глубины, количества элементов и ожидающих запросов; признаки полноты и усечения;
- порядок событий и результата, поздние ответы, область уникальности и срок действия идентификаторов, повторный запрос и ограниченный срок хранения исходов. Определить проверяемое окно дедупликации; просроченный/чужой ID отвергается по выбранному контракту, а не превращается в новую команду. Не обещать exactly-once за пределами доказанной модели;
- прекращение ожидания по timeout без скрытого повторения принятой команды; запрос состояния по исходному идентификатору, если его можно поддержать;
- принадлежность результатов и подписок исходному владельцу, правила завершения при отключении и отсутствие автоматического присвоения работ после reconnect.

Одноразовое чтение не обязано иметь весь набор состояний длительного выполнения. Контракт вводит только состояния, которые реализация способна подтвердить. Метки «очистка завершена» или «эффектов нет» без доказательств недопустимы.

**Проверки:** автономная валидация пограничных сообщений и таблиц переходов: несовместимая версия, неизвестный метод, неполные/лишние параметры по принятой схеме, неверный владелец, устаревшая среда, timeout до/после принятия, поздний ответ, ошибка после игрового действия. Тесты подтверждают различимые последствия, а не повторяют сериализатор.

**Условие завершения:** для каждого исхода известно, что возвращает MCP-клиенту сервер, что известно об эффектах и что можно делать дальше. Контракт согласован с фактическими возможностями канала и не обещает неподтверждённую отмену/очистку.

## 8. Э3 — минимальная сквозная вертикаль

**Результат:** реальный MCP-вызов проходит через выбранный сервер и официальный мод до игрового API.

Предстоящие действия:

1. Создать официальный пакет с проверенным идентификатором, дескриптором, версией и минимальными AngelScript-файлами. Начать с самостоятельной регистрации, если она подтверждена, без изменения игровых механик.
2. Реализовать согласованную точку обработки и жизненный цикл: загрузка, доступность транспорта, готовность контекста/мира, завершение. Проверки объектов и переходы состояния — по подтверждённым API.
3. Создать внешний сервер на выбранном SDK, адаптер канала, handshake/status и одну операцию чтения. До готовности игрового обработчика не объявлять инструмент рабочим.
4. Отделить обнаружение/подключение, ожидание ответа и выполнение операции. Проверять сообщения обеих сторон; диагностировать неверный результат отдельно от игрового отказа.
5. Использовать корреляционные идентификаторы в минимальной диагностике. Не сохранять полные игровые данные и пользовательские пути без необходимости.
6. Проверить через реальный MCP-клиент успешный ответ и различимые отказы: сервер доступен, мод отсутствует; мод загружен, канал недоступен; канал открыт, мир не готов; ответ повреждён; операция успешна.
7. Измерить стоимость вертикали и выбрать рабочие ограничения по результатам. Если канал не укладывается в назначение, вернуться к Э1 и актуализировать план до расширения инструментов.

**Условие завершения:** из MCP-клиента получено проверенное игровое значение с подтверждённым происхождением. Ошибки слоёв различимы, timeout не вызывает повтор, минимальный lifecycle проверен. Это промежуточная контрольная точка; согласованный полный объём ещё может оставаться незавершённым.

## 9. Э4 — каталог возможностей, диагностика и справочник API

**Результат:** клиент узнаёт, что умеет мост, что доступно сейчас и на каком основании.

Для операции каталог описывает имя, назначение, схемы аргументов и результата, эффекты, необходимый контекст, реализованность, текущую доступность, причину недоступности и источник проверки. Ревизия каталога либо иной согласованный механизм отражает изменение среды без выдачи старого состояния за текущее.

Различать пять фактов: API описан; присутствует в исследуемой сборке; обработчик реализован; вызов проверен в нужном контексте; операция доступна сейчас. Наличие одного не означает остальные.

Предстоящие действия:

1. Определить минимальный каталог статуса и готовности для первой вертикали; расширять его вместе с инструментами.
2. Подготовить локальный индекс официального Modkit: типы, функции, параметры и ссылки на исходники. Отдельно обозначать статический индекс и runtime-наблюдения; не обещать полный обход нативной рефлексии.
3. Определить идентичность используемого справочника: ревизия, охват и соответствие целевой игре. Обновление внешнего Modkit не должно незаметно менять подтверждения рабочего моста.
4. Обеспечить ограниченные ответы, поиск и навигацию по источникам. Выбирать объём индекса по фактической структуре API, не импортировать все сторонние материалы без необходимости.
5. Разделить независимые локальные инструменты сервера и требующие игры операции. Недоступный мир не должен делать статический справочник недоступным.
6. Добавить диагностику текущего соединения, среды и ограничений; параметры канала остаются в серверной конфигурации, игровые скрипты не получают абсолютных путей установленной игры.
7. Определить инструменты разработки официального пакета: создание/проверка `GothicMod.json`, поиск и редактирование исходников в выбранной рабочей базе, диагностика компиляции и управление подтверждённым reload. Для каждой операции отделить локальное действие сервера от воздействия на игровую среду. Поддержка редактора/cooking проектируется отдельно, когда подтверждён способ интеграции; UE 5.8 MCP не объявляется частью G1R.

**Проверки:** каталог до/после готовности мира и инвалидирования среды; отказ отсутствующей возможности с объяснением; статический справочник при отключённой игре; полнота/усечение поиска; несоответствие ревизии справочника и игры.

**Условие завершения:** клиент может определить доступный следующий шаг по структурированным сведениям. Непроверенный API не рекламируется как рабочая игровая команда.

**Фактический результат R3 / 1.0.0-dev.1:** создан stdio MCP-сервер со статусом, каталогом, поиском файлов/текста, чтением исходников, лексическим индексом типов и структурной проверкой пакетов. Рабочие корни заданы явно; все семь операций read-only и возвращают структурированный результат либо ошибку. Игровые группы обозначены нереализованными. На реальном Modkit проверены локальные запросы; отдельная MCP stdio-сессия на изолированных данных вызвала все инструменты. Это независимая часть Э4, а не завершение Э3 или полного выпуска. Реестр нативного API, изменение/создание пакетов, компиляция и reload пока не реализованы. [Контракт локальных инструментов](../local-tools.md).

## 10. Э5 — объекты и снимки состояния

**Результат:** полезные ограниченные операции чтения через проверенные официальные API.

1. Выбрать небольшой конкретный набор игровых объектов и значений по назначению версии. Каждый класс, поле и способ получения подтверждается источником; универсальный обход всего графа не является обязательным стартом.
2. Определить непрозрачные ссылки вместо долговечных сырых адресов. Ссылка содержит проверяемую принадлежность среде и поколению; владение клиентом вводится там, где требует выбранная модель.
3. Проверять действительность объекта в момент чтения. Кэш не даёт права считать его живым после загрузки мира или скриптового изменения.
4. Возвращать копии данных с типом, происхождением, полнотой и сведениями об усечении. Не отдавать внешнему клиенту изменяемые игровые структуры как владение данными.
5. Определить согласованность снимка: единое чтение в подтверждённой точке либо последовательные чтения, между которыми состояние могло измениться. Не называть результат атомарным без доказательства.
6. Ограничить число объектов, полей, глубину, время/бюджет обработки и объём ответа. Пагинация или разбиение работы вводится только с понятной семантикой и подтверждённой точкой продолжения.
7. Сравнение снимков строить на копиях. Исчезнувший объект, неполный охват и изменение поколения должны отличаться от изменения значения.

**Проверки:** существующий/отсутствующий объект, неверная и устаревшая ссылка, чужой владелец при применимой политике, уничтожение объекта между поиском и чтением, смена мира, неподдерживаемый тип, превышение объёма, частичный результат. Сначала автономные модели, затем минимальные разрешённые игровые проверки.

**Условие завершения:** согласованный набор значений читается воспроизводимо; неверные ссылки не приводят к обращениям к старым объектам; границы и согласованность результата видны клиенту.

## 11. Э6 — наблюдения и подписки

**Результат:** ограниченная наблюдаемая работа с определённым владельцем и жизненным циклом.

1. Выбрать сначала один подтверждённый источник события или набор наблюдаемых значений. Решение «событие или опрос» зависит от API и стоимости; произвольные hooks, таймеры и частота опроса заранее не назначаются.
2. Определить старт, срок жизни, остановку, получение результата и завершение подписки. Timeout ожидания старта отличается от длительности самой подписки.
3. Привязать работу к клиенту и поколению среды. Если сервер объединяет клиентов в одно игровое соединение, правила владельцев сохраняются на всех слоях.
4. Ограничить буферы в моде и сервере, назначить последовательность событий и явные сведения о потерях. Отсутствие доставленного события не является доказательством отсутствия игрового события.
5. Определить порядок подтверждения старта, событий и финального состояния, в том числе завершение до доставки подтверждения.
6. Проверить остановку и очистку. Различать удаление регистрации, её нейтрализацию и завершение уже вошедшего callback; сильное подтверждение выдаётся только при наличии источника.
7. Зафиксировать поведение при отключении клиента, закрытии сервера, смене мира и reload. Reconnect не присваивает старую подписку и не запускает её скрыто снова.

**Проверки:** две независимые работы, остановка одной без влияния на другую, переполнение обоих слоёв, disconnect до/после старта, неопределённый результат старта, invalidation во время callback, потерянный финальный ответ. Несколько клиентов проверяются, если входят в выбранный объём; при одном клиенте ограничения явно отражаются в каталоге и контракте.

**Условие завершения:** события доставляются с известными пределами, владелец управляет своей работой, завершение и фактическая очистка не смешиваются. Недоказанная очистка остаётся явно неполной.

## 12. Э7 — типизированные игровые действия

**Результат:** конкретный подтверждённый набор изменяющих команд в полном объёме версии.

Группа действий включена пользователем в полноценный объём 1.0.0, но конкретный перечень ещё не определён. До реализации выбираются полезные команды, их подтверждённые эффекты и пределы. Само наличие инструмента не разрешает менять сохранения, постоянную конфигурацию, баланс или механику конкретного мода без поручения на соответствующую задачу.

Для каждой включённой операции:

1. Подтвердить точную сигнатуру, условия вызова и допустимый контекст; описать параметры и результат.
2. Определить проверку текущего состояния, действительности объекта и владельца. Проверки входят в согласованный контракт, а не добавляются как несогласованные fallback-механизмы.
3. Зафиксировать границу принятия и начала эффекта. После возможного исполнения потеря ответа означает неопределённость, а не право повторить действие.
4. Определить отмену до/после начала, если она подтверждена; не обещать откат без API и доказательств.
5. Проверить преобразование результата после действия: failure сериализации не должен давать ложное «не выполнено».
6. Обеспечить понятное включение/отключение группы и откат версии через один осмысленный коммит согласно проектным правилам.
7. Пройти автономные проверки параметров/состояний и разрешённую минимальную игровую проверку эффекта. Для необратимого или затрагивающего пользовательские данные действия предварительно требуется соответствующее решение.

**Условие завершения:** готовность подтверждена для каждой согласованной команды, включая отказ и неопределённый исход. Неподтверждённый `eval` не подменяет отсутствующие типизированные инструменты. Если действия не включены в первую версию, это решение отражается в её объёме; в отложенный реестр они попадают только по прямому указанию пользователя.

## 13. Э8 — восстановление и итоговая приёмка

**Результат:** принятый объём работает в целевой среде и честно сообщает о нарушениях связи и lifecycle.

Матрица обязательных сценариев уточняется под реализованный набор:

| Сценарий | Ожидаемое свойство |
| --- | --- |
| Отключение до отправки / до принятия | Определённый отказ без ложного подтверждения исполнения |
| Отключение после принятия | Исход и эффекты не выдумываются; нет скрытого повтора |
| Timeout и поздний ответ | Ответ относится к исходному запросу и не попадает следующему |
| Повторный / просроченный идентификатор | Повтор в подтверждённом окне не вызывает второе действие; за его пределами действует явно определённый отказ, забытый ID не становится новой командой |
| Мир не готов / смена мира во время запроса | Отказ или результат объяснимы; старые ссылки и работы не переходят в новую среду |
| Reload / restart | Различается инвалидирование скриптов и процесса; поколение меняется по подтверждённому правилу |
| Неверная/устаревшая ссылка | Нет обращения к неподтверждённому объекту |
| Переполнение и чрезмерный ответ | Ограничения и потери сообщены, очереди остаются ограниченными |
| Ошибка обработчика / повреждённый пакет | Диагностика различает уровень ошибки; состояние последующих запросов определено |
| Закрытие сервера / прекращение клиента | Работа завершается по владельцу; очистка отражает фактическое подтверждение |
| Несколько клиентов при поддержке | Результаты, отмены и подписки не смешиваются |
| Независимый статический справочник | Доступен согласно контракту при отсутствии игры |

Проверки разделяются на автономную логику, адаптер канала, сквозные MCP-проверки и разрешённую игровую приёмку. Для будущего набора создаётся `docs/tests/G1R_MCP/README.md` с реальными командами, постоянными сценариями и границами подтверждения; исполняемые тесты остаются отдельно.

Измеряются задержка, верхний проверенный объём, стоимость обработки и стабильность при выбранном сценарии нагрузки. Численные критерии фиксируются после исходных замеров и проверки потребностей; отсутствие crash в одной пробе не означает общую стабильность.

**Условие завершения:** все включённые в объём требования покрыты соответствующими проверками; оставшиеся ограничения названы и согласованы. Нет скрытого повторения команд, ложной готовности или неподтверждённых заявлений об очистке. Широкий прогон выполняется для итоговой приёмки; повторение уже прошедших проверок нужно только после влияющих изменений, ошибки или непокрытого риска.

## 14. Э9 — упаковка и выпуск

**Результат:** воспроизводимый комплект из исходников подпроекта с согласованной версией и реальными инструкциями.

1. Определить окончательный идентификатор и корень официального пакета по проверенному `GothicMod.json`; подготовить необходимый AngelScript и комплект внешнего сервера.
2. Создать воспроизводимую проверку/упаковку из Git. Для скриптового пакета отличать структурную проверку от реальной компиляции игрой; наличие ZIP не подтверждает загрузку мода.
3. Проверить зависимости, способ запуска сервера, канал и условия обычного/development режима. `dependencies` с `name: "G1R"` и `requiredVersion` содержит подтверждённые ограничения версии игры, а не примерную версию из руководства.
4. Согласовать точный комплект поставки. Исходники, инструменты разработки и диагностические артефакты включаются по назначению, без случайного попадания локальных данных.
5. Проверить соответствие публичной версии в коде/дескрипторе, README, выпускных материалах, артефакте и тестах. Каждый предыдущий функциональный коммит имеет уникальный `dev.N`; выпуск заменяет последний `-dev.N` публичной версией отдельным release-коммитом.
6. Подготовить краткий changelog по фактическому diff и истории разработки, включая ограничения. Внутренние `dev.N` не оформляются отдельными публичными релизами.
7. Подготовить инструкции по проверенному способу установки/запуска и быстрому отключению. Сборка комплекта не означает его установку или публикацию.
8. После выполнения всего согласованного объёма обработать PLAN-001 и синхронно архивировать его с обновлением реестров. Если завершена только первая вертикаль, план остаётся активным.

**Условие завершения:** комплект воспроизводится из зафиксированной базы, соответствует принятому объёму, проверенной среде и версии. Реальная установка/запуск и публикация выполняются только при соответствующих прямых поручениях и не объявляются сделанными по факту упаковки.

## 16. Решения и ограничения перехода к работе

| Решение / разрешение | Когда необходимо | Текущее состояние |
| --- | --- | --- |
| Начать исследование / реализацию | Перед реальной работой, выходящей за подготовку плана | Прямо поручено 30.10.2026 |
| Публичная версия и объём | До рабочего кода; детали уточняются по API | 1.0.0; полноценный инструмент ИИ-разработки модов |
| Обычный запуск или development mode | После сравнения фактической пригодности и последствий | Проверено в development mode через Steam |
| Транспорт и точка исполнения | До полноценной вертикали | Автономная DLL, loopback TCP, FEngineLoop::Tick; runtime-проверка пройдена |
| Собственный нативный маршрут | До соответствующих изменений | Прямо поручен и реализован для внутреннего применения |
| UE4SS backend / возврат mailbox | До соответствующих изменений | Не используются |
| Перечень игровых действий | До Э7 | Не определён |

| Загрузка экспериментальной DLL | В пределах порученного нативного маршрута | Выполнена из каталога подпроекта; игровые файлы не копируются |
| Установка / deploy официального пакета | До изменения установленного мода | Не поручено |
| Изменение cache, сохранений, постоянных настроек запуска или игровой конфигурации | До соответствующего изменения | Не поручено; разовые startup-флаги не означают разрешения удалять cache |
| Публикация / push / PR | До внешнего действия | Не поручено |

В будущей явно назначенной разработке необходимые проверки в уже работающей игре выполняются самостоятельно в её согласованном объёме. Сначала проверяется доступность подключённого G1R UE4SS Lua Bridge MCP; если его нет, это сообщается пользователю. Такой мост может быть исследовательским источником при наличии нужного API, но его наличие не является доказательством работы официального G1R MCP. Он не заменяет проверку нашего AngelScript-пакета.

Загрузка нового официального пакета и изменения, требующие restart, не объявляются возможными в уже работающей игре без подтверждения. Для будущих экспериментов рассматривается документированный внешний каталог и разовые `-Mods` / `-ModsDirectory`, после соответствующего поручения. Постоянные параметры Steam, установленный мод, precompiled cache и сохранения не меняются ради удобства проверки.
